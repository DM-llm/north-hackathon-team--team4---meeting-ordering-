## 1. RFC 多人协作 AI Coding

本次 Hackathon 的核心是体验一次 **以 RFC 为协作载体的多人 AI Coding**：三名成员先通过 RFC 讨论方案、对齐边界和分工，再使用 **North Studio、North Coder 和 N2** 协作完成一个可以现场运行的 Agent 应用。

本次 Topic 为 **会务系统 / 点餐系统（二选一）**。每组选择一个方向，在规定时间内完成设计、开发和演示。RFC 不限定模板、篇幅或数量，重点是让讨论形成的共识真正进入分工和代码实现。

最终作品需要让 Agent 真正参与业务过程：理解自然语言，将需求转换成结构化状态或约束，完成预约或推荐，并能继续处理冲突、修改和撤销。仅完成页面、表单或预设演示不算完成赛题。

注意：最终提交以 GitHub 上的 **submission tag** 为准，注意及时推送！

两个 Topic 的具体功能、基础开发场景和挑战方向见第 4 节。

### 4.1 Topic A：会务系统

#### 场景目标

为团队设计一个由 Agent 驱动、本地可运行的会议室查询与预订系统。只需要通过自然语言，管理员就可以配置会议室、开放时间和预订规则，成员可以预订会议室；配置结果必须真正进入系统状态并参与后续冲突校验。

系统以我们实际使用的空间为基础：

- **活动室**：中午作为餐厅，午餐时段不能预约会议；
- **会议室一、会议室二**：既可以分别使用，也可以合并成一间大会议室；
- **503、505、506**：三间小会议室，其中 **505 每周二全天不可用**。

团队可以根据产品设计补充容量、设备和位置等信息，但不得改变以上空间关系和固定规则。

#### 基础功能

1. **自然语言配置 Agent**：管理员可以用自然语言新增或修改会议室、容量、设备、开放时段和不可预约规则。
2. **会议室列表**：展示会议室名称、位置、容量、设备等基础信息。
3. **日历或时段视图**：查看会议室在指定日期或时段的占用情况。
4. **创建预约 Agent**：成员可以用自然语言预订，Agent 自动处理会议室、日期、开始时间、结束时间并填写会议信息。
5. **冲突校验**：同一会议室的重叠时段不得被重复预约；冲突时给出清晰提示。
6. **取消预约**：用户能够取消已有预约，并释放对应时段。

#### 挑战功能

- **合并会议室**：两个或多个可组合空间在时间和容量上保持一致；
- **动态禁用**：支持维护、活动、午餐等临时不可预约时段；
- **管理员调整**：管理员能够修改、取消或强制调整已有预约；
- **地图/平面图视图**：在空间视图中查看会议室位置和状态。

#### 基础场景

实现过程中，可以先用下面几个场景检查查询、预约、规则和状态是否真正连通：

- 下周二 10:00—11:00 想约一间小会议室开项目讨论，帮我看看有哪些可以用。
- 明天中午想预约活动室开会。
- 本周五 14:00—16:00 要开一场大会议，帮我把会议室一和会议室二合并使用。
- 这周三 504 临时维修，全天不能预约。刚才说错了，只停用下午。

跑完后可以检查：

- Agent 正确理解输入；
- 502 不会出现在周二的可用结果中；
- 活动室的午餐用途会真实阻止中午的会议预约；
- 会议室一和会议室二合并期间不能再被分别预约；
- 对 504 的连续修改只更新同一条规则，并反映在会议室和日历状态中。

### 4.2 Topic B：点餐系统

#### 场景目标

为多人聚餐设计一个由 Agent 驱动的点餐推荐系统：从菜单图片中获取菜品信息，每名成员都可以用自然语言提出自己的口味、忌口和其他需求，Agent 将多人约束与预算合并后输出一份可解释的推荐组合。

#### 基础功能

1. **菜单输入**
2. **多人自然语言需求 Agent**：每名成员都可以分别用自然语言提出偏好、忌口、过敏、辣度、甜度或其他限制。
3. **预算设置**：输入总预算，并以预算作为推荐约束。
4. **推荐组合**：Agent 根据菜单、人数、预算和所有成员约束生成一份点餐方案。
5. **总价与推荐理由**：展示方案总价，并解释关键选择、已满足约束和无法完全满足的条件。

#### 挑战功能

- **菜单图片上传与识别**：上传菜单图片，识别菜名、价格及可识别的菜品信息，并且关联到后续用户偏好约束（比如辣度）；
- **人工校正**：用户能够修正识别错误、补充缺失价格或调整菜品信息；
- **满减与优惠**：支持优惠券、满减门槛或套餐价格；
- **多目标优化**：同时权衡预算利用率、偏好覆盖和菜品多样性；
- **菜品共享**：在预算范围内，多人可以共享一份菜品；
- **替代方案**：在约束冲突或菜品不可用时提供备选组合；
- **为他人打包**：为不在现场的人单独生成满足其约束的打包方案，并计入预算和份量。

#### 基础场景

示例文字菜单：

```
招牌牛肉饭 48元
宫保鸡丁饭 36元
鱼香肉丝饭 34元
番茄鸡蛋饭 28元
麻婆豆腐饭 32元
酸菜鱼饭 42元
黑椒牛柳饭 46元
照烧鸡腿饭 39元
清炒时蔬饭 26元
花生酱拌面 30元
扬州炒饭 33元
香辣猪蹄饭 45元
```

实现过程中可以先用下面的多人需求检查完整链路：

- 这次一共 5 个人，总预算 250 元。
- 成员 A：我完全不吃辣。
- 成员 B：我可以吃微辣，但不吃猪肉。
- 成员 C：我对花生过敏。

跑完后可以检查：

- Agent 分别保存每名成员的自然语言需求；
- 菜单识别结果允许人工校正；
- 推荐方案同时考虑预算、人数和个人约束；
- 输出总价、推荐理由、已满足约束和无法满足的冲突；
- 任一成员追加或修改需求后，Agent 能重新生成方案。

## 5. 作品形态与实现边界

### 5.1 必须满足

- 作品必须提供 **本地可运行的 Web 应用入口**；Agent Runtime 可以按下述方式在本地或云端运行；
- 必须能够通过真实前端操作完成核心业务链路；
- 必须包含实际运行的 Agent 层：接收自然语言、形成结构化状态或约束，并调用业务能力完成配置或推荐；
- 仅使用固定表单、关键词判断或预先写死答案，不能视为完成 Agent 要求；
- 前端不要求公网部署；
- Agent Runtime 推荐以下三种方式（其他框架也可以，但是 LLM API 必须使用 `nex-agi/Nex-N2-Pro`）：
  - 使用 **NexAU** 在本地运行；
  - 使用 **North Coder** 作为本地 Runtime；
  - 使用 **NAC** 作为云端 Runtime；
- 团队需要在 README 中说明所选 Runtime 和可复现的启动步骤；
- 不要求连接真实日历、支付、餐厅、会议室或其他外部生产系统；
- README 必须提供清晰、可复现的安装和启动命令；
- 现场演示必须基于截止时冻结的 Git 版本启动。

### 5.2 允许使用

- Vite、Next.js 等通用项目脚手架；
- 正常的开源框架、组件库和依赖；
- 团队在比赛期间自行编写的辅助脚本和测试。

### 5.3 不允许使用

- 比赛开始前已经完成的会务系统或点餐系统业务实现；
- 将赛前业务代码复制到开赛后新建的仓库；
- 不能在 README 中说明来源、许可证或用途的关键外部代码。

## 7. RFC 协作

RFC 是团队讨论方案和避免并行冲突的协作载体。各组按 RFC 开发方法执行，并将 RFC 工件保留在仓库的 `docs/rfcs/` 下。

本次比赛不限定 RFC 的内容、模板、篇幅或数量；评分关注 RFC 是否真实承接了方案讨论、协作分工和实现过程，而不是文档格式。功能代码采用什么分支或 PR 流程不作限制。

## 8. GitHub Repo 创建方式及要求

### 8.1 创建时间与可见性

- 必须在 **正式开赛后** 新建仓库；
- 仓库必须设为 **Public**；
- 禁止使用赛前已存在的业务仓库作为提交仓库；
- 建议由一名成员创建仓库，并立即邀请另外两名成员共同开发。
- 推荐命名：`north-hackathon-team-<组号>-<meeting|ordering>`

### 8.2 通过 GitHub 网页创建

1. 登录个人 GitHub；
2. 点击 **New repository**（https://github.com/new）；
3. 按推荐规则填写仓库名；
4. Visibility 选择 **Public**；
5. 创建仓库；
6. 在 **Settings → Collaborators** 中邀请另外两名成员；
7. 三名成员分别确认自己的 Git 用户信息后开始提交。

### 8.3 每名成员确认 Git 身份

```bash
git config user.name
git config user.email
```

如信息不正确，在仓库内设置：

```bash
git config user.name "你的 GitHub 用户名"
git config user.email "你的 GitHub 提交邮箱"
```

三名成员不得共用同一个 Git 作者身份，否则检测脚本无法正确识别贡献。

### 8.4 最低仓库结构

```
.
├── README.md
├── docs/
│   └── rfcs/
│       └── 0001-<topic>.md
├── <应用源码>
├── <依赖清单与 lockfile>
└── <必要的配置示例>
```

README 至少包含：

- 团队成员与 GitHub 用户名；
- 选择的 Topic；
- 已完成功能；
- 本地安装与启动命令；
- 演示入口和测试数据；
- 三名成员的主要贡献；
- 关键第三方依赖及用途；
- 已知限制。

### 8.5 协作要求

- 分支和 Pull Request 流程不作强制要求；
- 评分和检测以最终仓库的完整 Git 历史为依据；
- 三名成员都应有真实、可说明的代码贡献；
- 提交应尽量保持小而清晰，避免三人共用作者、集中代提交或只在最后一次性导入代码；
- 自动生成文件、lockfile、格式化结果和大体积静态素材不能单独证明有效贡献。

### 8.6 截止与版本冻结（重要，涉及评分脚本）

代码截止前，团队必须完成：

```bash
git status
git add .
git commit -m "chore: finalize hackathon submission"
git push origin main
git tag submission
git push origin submission
```

如没有待提交内容，可跳过 `git add` 和 `git commit`，直接确认当前版本并打 tag。

截止版本统一以 **submission tag 指向的 commit** 为准。截止后不得移动或重建 `submission` tag。

### 8.7 现场启动核验

Showtime 开始前，团队需展示：

```bash
git status
git rev-parse HEAD
git rev-parse submission
```

要求：

- `git status` 为 clean；
- 当前 `HEAD` 与 `submission` 指向同一 commit；
- 从该版本按 README 命令启动应用；
- 现场演示的应用必须与 GitHub 截止版本一致。

## 10. 评分维度

评分总分 100 分：

**客观分：30 分，脚本自动计算**

- Git Commit 贡献均衡：15 分（三名成员贡献越平均，得分越高；只有一人贡献得 0 分）
- RFC 使用：15 分（GitHub 仓库中每人提交都存在 RFC 文件得 15 分，否则得 0 分）

**Peer 互评：70 分**，参赛者从以下六个方向按 0–5 分互评：

- 问题与用户价值：15 分
- 产品完成度：15 分
- 技术实现质量：15 分
- 创新与差异化：10 分
- 验证与实际效果：10 分
- Demo 与答辩：5 分

系统自动排除自评，并取有效评分的平均值。

```
最终总分 = Git Commit 分（15）+ RFC 分（15）+ Peer 互评分（70）
```

此外，在 North Studio 中使用 North Coder + `nex-agi/Nex-N2-Pro` 是进入正式排名的硬性条件，不属于普通加分项。
